# O-school(リポジトリ名: school-portal)

**O-school** は、学年別の今日の時間割・課題・行事・出席状況、地域情報サービス「大空町のお店」(東藻琴・女満別のグルメ・観光の口コミ)、
そして週1本ペースを目安に更新する「O-schoolの記事」を1つにまとめた、**生徒が毎朝自然に開くことを目的とした**生活ポータルWebサービスです。

> **O-schoolは学校が公式に提供・監修するサービスではありません。個人が開発・運営する非公式サービスです。** サイト内では特定の学校名を表示しない設計にしています。

デモ用の学校は「青葉台高等学校」(架空)として内部データ上は存在しますが、サービス名・UI上には一切表示されません。コードはそのまま実際の学校の運用に転用できるように作られています。

> 🚀 このリポジトリは `npm install && npm run db:migrate && npm run db:seed && npm run dev` の4コマンドで、
> デモデータが入った状態からすぐに全機能を触れます。詳しくは [8. ローカル起動方法](#8-ローカル起動方法) へ。

## 1. サービス概要

**「O-schoolを開けば、今日の学校生活が一目で分かる」** を目指した個人開発サービスです。単なるモックアップではなく、

- 初回アクセス時点でデモデータが入っており、全機能をすぐに体験できる
- 実際にインターネット上へ公開できる構成になっている
- 少人数のユーザーでも広告により継続的な収益が発生する可能性がある

ことを前提に設計・実装しています。トップページは「毎朝開くダッシュボード」として、今日の時間割 → 次の授業 → 明日の時間割 → 今日・近日の課題 →
次の行事 → 今月の授業 → 大空町のお店の新着口コミ → O-schoolの記事、という優先順位でユーザーが自然に回遊できる構成にしています
(設計の詳細は[11章](#11-改修の設計メモ全2回分))。

**デモ校情報(内部データのみ。UIには表示されません)**

| 項目 | 内容 |
|---|---|
| 学年・クラス | 高校1年(1年A組)/ 高校2年(2年A組)/ 高校3年(3年A組・3年B組) |
| デモ基準日 | 2026年9月(実行時点の日付に応じて「今日」「今月」は自動で切り替わります) |
| 地域情報 | 大空町(東藻琴・女満別) |

## 2. 機能一覧

### 生徒向け機能

- ✅ **毎朝開くダッシュボード(トップページ)**: 挨拶+今日の日付 → TODAY(今日の時間割、現在の授業/次の授業をハイライト)→ 明日の時間割 → 今日・近日の課題 → 次の行事・出席率 → お知らせ → 今月の授業 → 大空町のお店の新着口コミ → O-schoolの記事、の順で表示し、コンテンツの区切りごとに広告枠を配置
- ✅ **学年・クラスに応じた**時間割(月間カレンダー/一覧、日付クリックで詳細、学年・クラス切り替えセレクター)
- ✅ 日付ごとの時間割変更(通常の行事上書きに加え、**短縮授業**や**特定の日だけの選択科目**にも対応)
- ✅ **選択科目**: 同じ時限に複数の候補授業がある枠に対応(週間ベース時間割・日付ごとの上書き時間割の両方で可能)。生徒はどちらを履修するか選択でき、時間割・教科回数の集計に反映される
- ✅ 今月の教科回数の自動集計(時間割データから算出。今月/来月/指定月を切替可能)
- ✅ **共有課題**(同じ学年・クラスの生徒が誰でも登録・閲覧できる、投稿者は匿名表示)と**個人課題**(自分だけに表示)の2種類。締切フィルター、完了チェック機能
- ✅ 学校行事一覧とカウントダウン
- ✅ 出席状況の自己管理(ドーナツグラフで可視化、**学校公式記録でない旨を明記**)
- ✅ **大空町のお店**: 東藻琴・女満別のグルメ・カフェ・スイーツ・買い物・観光・その他のお店情報、写真投稿、星評価付き口コミ、通報
- ✅ **O-schoolの記事**: お店紹介・勉強法・学校生活コラム・地域イベント・開発日記などの読み物。カテゴリー別一覧・詳細ページ・関連記事表示
- ✅ サイト内横断検索(時間割・教科・課題・行事・お店・記事)
- ✅ アカウント管理(ニックネーム変更・パスワード変更・**学年/クラスの変更**・自分のお店投稿/出席/課題の確認)
- ✅ お問い合わせフォーム

### 管理者向け機能(`/admin`)

- ✅ ダッシュボード(ユーザー数・店舗数・未対応の通報/問い合わせ数などの概況)
- ✅ 週間ベース時間割の編集(学年・クラスを切り替えて編集、1つの枠に複数教科を追加すると自動的に「選択科目」として扱われる)
- ✅ 日付ごとの時間割変更の追加・削除(短縮授業・行事日・特定の日だけの選択科目もGUIで設定可能)
- ✅ 教科の追加・編集・削除(名前・カラー)
- ✅ 課題の追加・編集・削除(対象学年・対象クラスを指定可能)
- ✅ 学校行事の追加・編集・削除
- ✅ お知らせの投稿・編集・削除
- ✅ **O-schoolの記事の作成・編集・削除**(タイトル・サムネイル・本文・カテゴリー・著者名・公開状態)
- ✅ **お店の管理**(店名・地域・カテゴリー・説明・営業時間・定休日・住所・地図リンクの追加編集削除)
- ✅ **お店の口コミ・写真モデレーション**(通報対応、非公開化/復元)
- ✅ ユーザーの利用停止・解除(管理者は自分自身を停止できない)
- ✅ お問い合わせの一覧・対応済み管理
- ✅ 広告枠ごとのON/OFF(枠の数は固定されておらず、ページのどこにでも追加可能な設計)、サイト全体の広告一括OFF
- ✅ 公開範囲モード(学校限定 / 一般公開 / ハイブリッド)の設定
- ✅ アクセス・収益ダッシュボード(未接続の指標は「未接続」と正直に表示。ダミー値を実数値として見せない)
- ✅ 収益シミュレーター(ユーザー数・訪問頻度・広告表示率・RPMから月収/年収を試算)

## 4. デザインコンセプト

正式サービス名: **O-school**。キーワードは **「O」× 白 × 水色 × 空 × 飛行機**。

- **ベースカラー**: 白(`--surface: #ffffff`)を基調に、淡い水色(`--bg: #f4f9ff`)で画面全体に「空」の余白感を出す
- **アクセントカラー**: 水色(`--primary: #0ea5e9`)。学校サイトにありがちな紺色・臙脂色ではなく、スマホアプリらしい軽やかな配色にした
- **ロゴ/ブランドシンボル「O」**: `src/components/Logo.tsx` に実装した円環(ドーナツ型)のマーク。大空町の「大空(おおぞら)= O」、地球・軌道・空を連想させる円をモチーフにし、ヘッダー・管理画面サイドバー・favicon・PWAアイコン・ログイン/登録画面・記事のデフォルトサムネイルで共通して使用
- **飛行機モチーフ**: 大量にイラストを配置するのではなく、`/events` の行事カウントダウンバッジに小さな飛行機アイコンを控えめに使用する程度に留めている(女満別空港が近い大空町らしさも意識)
- **「学校サイトっぽくしすぎない」**: 角丸カード・rounded-full のボタン/バッジ、ボトムタブナビゲーション、スマホアプリのようなカード型レイアウトを徹底し、静的な学校ホームページとは一線を画すデザインにしている
- **学校名を出さない**: ロゴ・ヘッダー・メタデータ・PWAマニフェストのいずれにも特定の学校名は表示せず、「O-school」のみをブランドとして統一している

配色トークンは `src/app/globals.css` の CSS変数(`--primary`, `--bg` 等)に集約しているため、色調整はそのファイルを編集するだけで全ページに反映されます。ダークモードにも対応済みです。

## 5. 技術構成

| 領域 | 採用技術 | 選定理由 |
|---|---|---|
| フロントエンド/バックエンド | **Next.js 16**(App Router, Server Components, Server Actions) | フロントとAPIを1つのプロジェクトで完結でき、Vercelとの親和性が非常に高い。個人開発でインフラを増やさずに済む |
| 言語 | TypeScript | 型安全性、Prisma/Zodとの統合 |
| スタイリング | Tailwind CSS v4 | 高速なスタイリング、軽量なCSS出力、モバイルファーストに強い |
| UIアイコン | lucide-react | 軽量なSVGアイコンセット |
| ORM/DB | **Prisma 5** + SQLite(開発)/ PostgreSQL(本番想定・Supabase) | スキーマ駆動でマイグレーションを管理でき、開発はファイル1つのSQLiteで完結。本番はSupabaseへ無停止で移行しやすい |
| 認証 | 自前実装(bcryptjs + jose製JWTセッションCookie) | 外部サービスに依存せず、個人情報(メールアドレス等)を収集しないログインID方式を実現するため |
| バリデーション | Zod | Server Actionsの入力値検証 |
| 画像アップロード | Server Actionの`FormData`で受け取った画像を base64 の data URI としてDBに保存 | 外部オブジェクトストレージを別途契約しなくても、Vercelのようなサーバーレス環境で即座に動く構成にするため |
| PWA | 独自Service Worker + `manifest.ts` + `next/og`によるアイコン生成 | 外部プラグインに依存せず、Next.js 16の仕様に完全準拠させるため |
| ホスティング(推奨) | **Vercel** | Next.jsの開発元。Server Actions/動的レンダリングをそのままサーバーレスで実行でき、無料枠が大きい |
| DB ホスティング(推奨) | **Supabase**(PostgreSQL) | 無料枠が大きく、Prismaと相性が良い。将来的な行数増加にも対応しやすい |
| ソース管理/CI | **GitHub** + Vercelの自動デプロイ連携 | pushするだけで本番反映、個人開発として最も省力 |

> **なぜCloudflare PagesではなくVercelか**: 本サービスはログイン・投稿・出席記録・画像アップロードなど「書き込みを伴う動的処理」が中心で、Next.jsのServer Actions(Node.jsランタイム上でPrismaやbcryptjsを実行)を多用しています。Cloudflare PagesはEdgeランタイム中心のため、Prismaのようなネイティブ依存のあるORMやNode.js APIをそのまま動かすには追加のアダプタ・構成変更が必要です。学生が最短で公開・運用するなら、Next.js特化のVercelが最も摩擦が少ないと判断しました。

> **画像アップロードの容量について**: `MAX_IMAGE_BYTES`(`src/lib/constants.ts`)で1枚あたり3MBに制限しています。投稿数・アクセスが増えてDBが肥大化してきた場合は、Vercel Blob / Supabase Storage / Cloudflare R2 などの専用オブジェクトストレージへ移行し、DBには参照URLだけを保存する構成に切り替えることを推奨します。

## 6. データベース構造

`prisma/schema.prisma` が正です。将来の複数校対応を見据え、

```
School(学校・内部データのみ) → Grade(学年) → Class(クラス) → User(ユーザー)
School → Subject(教科)
Class → TimetableSlot(週間ベース時間割: 曜日×時限。同じ枠に複数行 = 選択科目)
Class → DailyOverride(日付ごとの時間割変更) → DailyOverrideSlot(その日の各時限。同じ枠に複数行 = その日だけの選択科目)
User + Class → ElectiveChoice(選択科目のうちどれを履修するかの個人設定)
User → Assignment(課題。visibility=SHARED/PERSONAL、gradeId/classIdで対象範囲を指定) → AssignmentCompletion
School → Event(学校行事)
User → AttendanceRecord(出席記録)
School → Announcement(お知らせ)
ShopRegion(東藻琴/女満別) → Shop(店舗) → ShopPhoto / ShopReview → ShopReport(通報)
ArticleCategory(記事カテゴリー) → Article(O-schoolの記事)
AdSlot(広告枠設定) / SiteSetting(公開範囲・広告ON/OFF) / Inquiry(お問い合わせ)

[レガシー・UIから撤去済み] User → Post(旧・汎用口コミ) → PostLike / Report
```

という階層構造にしています。`School`は時間割・行事等を束ねる内部データとしてのみ存在し、名前をUIに表示することはありません。
`classId` / `schoolId` / `gradeId` を主キーとして関連テーブルに持たせているため、将来複数校に対応する際もテーブル設計の大きな変更なしで拡張できます。

**SQLiteの制約について**: SQLiteはPrismaのネイティブenumをサポートしないため、`role` `status` `category` `visibility` 等はDB上は`String`列にし、
`src/lib/constants.ts` でTypeScriptのユニオン型として型安全性を担保しています。PostgreSQLへ移行してもこの設計はそのまま使えます。

**選択科目の表現方法**: `TimetableSlot`・`DailyOverrideSlot` それぞれの一意制約を `(period)` 単位ではなく `(..., period, subjectId)` にすることで、
同じ「クラス・曜日(または日付)・時限」に複数の教科行を登録できるようにしました。2行以上あれば自動的に「選択科目」としてUI上で扱われ、`electiveGroup`列で
「文理選択」のようなグループ名を付けられます。生徒個人がどちらを履修するかは `ElectiveChoice` テーブルに保存し、時間割表示・教科回数集計の両方に反映されます。

## 7. 認証

- パスワードは `bcryptjs` でハッシュ化して保存(平文・逆算可能な形では一切保存しない)
- ログイン状態は `jose` で署名したJWTを **httpOnly Cookie** に保存(XSSで盗み出せない、JSからアクセス不可)
- CSRF対策: Next.js Server ActionsのOriginヘッダー検証(標準機能)
- 認可は **多層防御**: `proxy.ts`(旧middleware)でのリダイレクト → 各レイアウト/Server Component/Server Actionでの`getCurrentUser()`/`requireAdmin()`再チェック
- メールアドレス等の個人情報を必要とせず、**ログインID + ニックネームのみ**でアカウント作成可能(登録時に学年・クラスの選択も必須)
- 自己登録には「参加コード(学校の合言葉)」が必要。同じコードで時間割・学校行事の閲覧ゲートも通過できる。DB(`SiteSetting.inviteCode`)で管理し、`/admin/security`からいつでも変更可能(デモ初期値は `aobadai2026`。未設定時のみ環境変数`SCHOOL_INVITE_CODE`にフォールバック)
- 管理者アカウントには任意で二段階認証(TOTP)を設定できる(`/admin/security`)。設定すると、パスワード確認後に認証アプリの6桁コード入力が必要になる

## 8. ローカル起動方法

```bash
cd school-portal
npm install

# .env を用意(サンプルをコピーして使用)
cp .env.example .env
# SESSION_SECRET は最低32文字のランダム文字列に変更してください
# SITE_URL は本番公開時に実ドメイン(例: https://example.com)に変更してください

# DBを作成してマイグレーションを適用
npm run db:migrate

# デモデータを投入(学年別の時間割・課題・行事・お店・記事などを一括生成)
npm run db:seed
```

## 11. 改修の設計メモ(全2回分)

初回リリース後、2回の大規模改修を行いました。影響範囲ごとに設計の要点を整理しています。

### 1回目の改修: 学年別時間割・選択科目・お店機能

| 項目 | 変更前 | 変更後 |
|---|---|---|
| 時間割 | 学校に1つの時間割(単一クラス想定) | `Grade`/`Class`単位で完全に独立。生徒は自分の学年・クラスの時間割だけを見る(設定で変更可能) |
| 時間割の1枠 | 必ず1教科 | 複数教科を登録可能。2教科以上=選択科目として自動判定 |
| 課題 | クラスに紐づく1種類のみ、管理者のみ登録可 | 「共有課題(学年/クラス指定)」と「個人課題(本人のみ)」に分離。生徒も登録可能、匿名表示 |
| 口コミ | 学校生活全般の汎用掲示板(`Post`) | **UI・ルートから撤去**。「大空町のお店」の口コミ(`ShopReview`)に一本化 |
| 地域情報 | なし | 「大空町のお店」機能を新規追加 |

**既存データの扱い**: 旧・汎用口コミ機能(`Post` / `PostLike` / `Report` テーブル)は**物理削除していません**。スキーマにそのまま残し、レガシーである旨のコメントを付けています。

### 2回目の改修: O-schoolへのリブランド・毎朝のダッシュボード化・記事機能

| 項目 | 変更前 | 変更後 |
|---|---|---|
| サービス名 | 「青葉台高校ポータル」(学校名を含む名称) | **「O-school」に統一。学校名はUIのどこにも表示しない**(非公式サービスである旨を利用規約・メニューに明記) |
| トップページ | 機能の一覧表示に近い構成 | 「毎朝開くダッシュボード」として優先順位を再設計: 挨拶+日付 → TODAY(現在/次の授業をハイライト)→ 明日 → 課題 → 行事 → 教科回数 → お店 → 記事、の順に固定 |
| 現在時刻の扱い | なし | `src/lib/schedule-time.ts` に時限ごとの目安時刻テーブルを追加し、現在時刻から「今の授業」「次の授業」を判定してハイライト表示 |
| 日付ごとの時間割変更 | 通常授業か休校かの上書きのみ、1コマ1教科 | **短縮授業**(コマ数を減らした上書き)や、**特定の日だけの選択科目**(`DailyOverrideSlot`にも複数行registered可能に)に対応 |
| 記事 | なし | 「O-schoolの記事」を新規追加。管理者が作成し、カテゴリー・サムネイル・著者・関連記事を持つ。投稿頻度は週1本を目安とするが、システム上の義務にはしていない |
| 広告 | 固定8箇所程度 | **トップページのセクション間に5箇所を追加**するなど、コンテンツの区切りごとに広告枠を配置できる設計に拡張(合計15箇所)。ただし個人課題タブなど非公開ページには表示しない |

**設計判断のポイント**:

- 「広告を増やすこと」自体を目的にせず、TODAYを起点に時間割→課題→行事→お店→記事へ自然に回遊できる導線を優先し、結果としてPV・広告表示機会が増える構造を目指した(ギガファイル便のような「広告枠を多く持つが押し付けない」設計を参考にしつつ、広告量そのものは模倣していない)
- 現在時刻による「今の授業」判定は、実際のチャイム時刻と一致しない場合があるため、`PERIOD_TIMES`(`src/lib/schedule-time.ts`)は学校ごとに調整することを想定した設定値として分離している
- 記事の著者名は既定で「O-school編集部」とし、個人名を出さない運用をデフォルトにしている(管理者が任意に変更可能)

## 12. Web公開方法(推奨構成: Vercel + Supabase)

1. **GitHubリポジトリを作成**し、このプロジェクトをpush
2. **Supabase**(https://supabase.com )で無料プロジェクトを作成し、Postgresの接続文字列(Connection string, `Session pooler`推奨)を取得
3. `prisma/schema.prisma` の `datasource db` を以下のように変更:
   ```prisma
   datasource db {
     provider = "postgresql"
     url      = env("DATABASE_URL")
   }
   ```
   > SQLiteで作成した既存のマイグレーションファイル(`prisma/migrations/*`)はSQLite専用のSQLが含まれるため、Postgresへはそのまま適用できません。`prisma/migrations` を一度削除し、Postgresの接続文字列に対して `npx prisma migrate dev --name init` を実行し、Postgres用のマイグレーションを作り直してください。
4. **Vercel**(https://vercel.com )でGitHubリポジトリをインポート
5. Vercelの Project Settings → Environment Variables に以下を設定:
   - `DATABASE_URL`: Supabaseの接続文字列
   - `SESSION_SECRET`: ランダムな32文字以上の文字列
   - `SCHOOL_INVITE_CODE`: 学校で使う招待コード(生徒に配布する合言葉)
   - `SITE_URL`: サイトの実URL(例: `https://example.com`)。末尾スラッシュなし。SEO(sitemap/robots/OGP)に使用
6. デプロイ実行 → `package.json` の `build` スクリプトは `prisma migrate deploy && next build` になっているため、デプロイのたびに未適用のマイグレーションが自動的に本番DBへ適用されます
7. デプロイ完了後、`npx prisma db seed` を本番DATABASE_URLに向けて一度だけ実行し、デモ(または実際の学校・地域の)データを投入

## 13. Cloudflare等の設定

Cloudflareは主に**ドメインのDNS管理**と**任意のCDN/保護機能**の用途で利用します(ホスティング自体はVercelを使う構成のため)。

- **Cloudflare Registrar**: ドメインを「原価」で購入できる(マークアップなし)ため、個人開発で費用を抑えたい場合の選択肢になります。ただし取扱いTLDが限定的(`.jp`は非対応)です
- Cloudflareでドメインを管理する場合、VercelのカスタムドメインへはDNSレコードを「DNSのみ(グレークラウド)」で設定するのが最もトラブルが少ない構成です
- Cloudflareを使わず、ドメインを取得したレジストラのDNS管理画面から直接Vercelを指すCNAME/Aレコードを設定するだけでも問題なく公開できます

## 14. 独自ドメイン取得方法

### ドメインとは

インターネット上の住所にあたる文字列です(例: `example.com`)。独自ドメインを取得すると、Vercelが割り当てる `xxxx.vercel.app` のような既定URLではなく、
サービス名を冠した覚えやすいURLで運用できます。AdSense等の広告審査でも、独自ドメインの方が信頼性評価の面で有利です。

### TLD(.com / .jp / .net 等)の違い

| TLD | 特徴 | 向いているケース |
|---|---|---|
| `.com` | 世界で最も普及したgTLD。登録に地域制限なし | 個人開発・将来的な一般公開を見据えるなら第一候補 |
| `.jp` | JPRSが管理する日本向けドメイン。連絡先情報の登録が必要 | 「日本のサービス」という信頼感を出したい場合 |
| `.net` | `.com`に次いで歴史が長いgTLD | `.com`が空いていない場合の代替 |
| `.co.jp` | 日本国内で登記された法人のみ登録可能 | **個人開発の本サービスでは登録不可** |

### サービス名 + ドメイン候補(10案)

O-schoolというブランド名を軸に、実際に購入する必要はありませんが検討の参考としてまとめています。

1. `o-school.app` — サービス名そのまま。最も直感的
2. `o-school.jp` — 日本向けサービスであることを明示
3. `oschool.dev` — 開発者色を出したい場合
4. `oozora-o.jp` — ブランドシンボル「O」と地域名(大空町)を掛け合わせた候補
5. `jikanwari-o.jp` — 「時間割」+「O」で機能と分かりやすさを両立
6. `myoschool.app` — 「毎日開く」ニュアンスを込めた候補
7. `todays-class.jp` — 「今日の時間割」という中心機能を表現
8. `oschool-life.com` — 学校生活+地域生活の両方を包含するイメージ
9. `oschool-navi.jp` — 「ナビ」という検索されやすいキーワード構成
10. `memanbetsu-o.jp` — 女満別に寄せた地域ガイド寄りの候補

### 取得手順の概要

1. レジストラを選ぶ(例: お名前.com / Xserverドメイン / Cloudflare Registrar 等)
2. 空きドメインを検索し、購入手続き(本人確認・支払い)
3. 取得したドメインの管理画面からDNSを設定(次項)

## 15. DNS設定

1. Vercelのプロジェクト → Settings → Domains → ドメインを追加
2. Vercelが指定するDNSレコード(通常は `A` レコード または `CNAME`)が表示される
3. ドメインのレジストラ(またはCloudflare)のDNS管理画面で、その内容の通りレコードを追加
4. 反映まで数分〜最大48時間程度かかる場合があります
5. Vercel側でドメインのステータスが「有効」になれば設定完了

## 17. 公開範囲の比較(学校限定 / 一般公開 / ハイブリッド)

公開方式は3パターンで比較検討した結果、本サービスは **3段階のアクセス範囲**(公開 / 参加コードゲート / ログイン必須)という
**A・B・Cのハイブリッド**を採用している(セキュリティ実装の詳細は[docs/SECURITY_AUDIT.md](docs/SECURITY_AUDIT.md)参照)。

| 観点 | A: 学校限定公開 | B: 一般公開 | 採用: 3段階ハイブリッド |
|---|---|---|---|
| 概要 | 全機能に招待コード付きログインが必須 | 誰でも全機能を利用可能 | 記事・お店(閲覧)は**完全公開**、時間割・行事は**参加コード(アカウント不要)**、課題・出席・設定は**ログイン必須** |
| セキュリティ | ◎ 最も閉じている | △ 誰でもアクセスできるため攻撃対象になりやすい | ○ 時間割は「O-schoolを知っている人」に絞りつつ、個人データはログインで保護 |
| 学校名の露出 | ◎ そもそもUIに学校名を表示しないため露出リスク自体が低い(全モード共通) | 同左 | 同左 |
| 時間割の公開 | 生徒のみ閲覧可 | 誰でも閲覧可 | **参加コードを知っている人のみ**閲覧可(アカウント登録は不要)。検索エンジンには載せない(noindex) |
| 広告収益 | ✕ 検索流入がなく、PVが伸びにくい | ◎ SEO流入が見込め、PVが最大化しやすい | ○ 記事・お店ページはSEO流入が見込める。時間割は広告表示自体は行うがSEO対象外 |
| SEO | ✕ ログインの壁があり検索エンジンにインデックスされない | ◎ 全ページがインデックス対象 | ○ 記事・お店(公開ページ)のみインデックスされ、「大空町 グルメ」等の地域検索流入が期待できる |
| 学校とのトラブル可能性 | ◎ 低い(学内限定のため) | △ 学校名を出していなくても、時間割等から在籍校が特定される可能性はゼロではない | ○ 参加コードで時間割の露出範囲を絞りつつ、学校名も出さないため二重にリスクを抑えられる |

**結論**: 「知らない人が学校の時間割を毎日確認できる状態は避けたいが、アカウント登録の手間はできるだけ減らしたい」という運用判断から、
時間割・学校行事は**参加コード(1つの合言葉、Cookieで180日有効)だけで閲覧可能**にし、アカウント登録は「課題・出席・選択科目・お店への投稿」など
本当に個人に紐づく機能を使うときだけ求める設計にした。参加コードは登録時の合言葉と共通で、管理画面(`/admin/security`)からいつでも変更できる。

## 20. AdSense等の広告申請準備

> 以下はGoogle公式ヘルプ(2026年9月時点でWeb検索・公式ページで確認済み)に基づく内容です。ポリシーは変更される可能性があるため、
> 申請前に必ず [Google AdSense ヘルプセンター](https://support.google.com/adsense) で最新情報を確認してください。

### AdSenseとは

Webサイトに広告を掲載し、表示回数やクリックに応じて収益を得られるGoogleの広告配信サービスです。

### 申請に必要なもの

- **独自ドメイン**
- サイトのHTMLソースにアクセスできること
- **オリジナルで高品質なコンテンツ**があること(時間割・課題・行事・大空町のお店情報・O-schoolの記事など独自コンテンツが揃っている)
- Googleのプログラムポリシーに沿ったコンテンツであること
- プライバシーポリシー・利用規約・お問い合わせページ(すべて実装済み)
- 運営者情報がある程度明確であること(非公式サービスである旨の明記を含む)

### 本人名義での申請について(運営者が成人の場合)

Google公式ヘルプ([AdSenseアカウントの年齢要件](https://support.google.com/adsense/answer/14230)、2026年9月確認)によると:

> **AdSenseプログラムに参加するには、18歳以上である必要があります。**

運営者が成人である場合は、**本人名義のGoogleアカウントでそのままAdSenseに申請できます**。

- 本人確認: 審査や支払い開始時に、Googleから氏名・住所等の情報や本人確認書類の提出を求められる場合があります(最新情報は[AdSenseヘルプ](https://support.google.com/adsense/answer/9724)を参照)
- 税務情報: 収益発生後、税務情報の登録が求められる場合があります
- 銀行口座: 収益の振込先として本人名義の銀行口座情報の登録が必要です
- 学校名を含まないドメイン: O-schoolは学校名を表示しない設計のため、ドメイン名についても特定の学校を想起させすぎる表現は避けることを推奨します

> 18歳未満で運営する場合は、保護者や後見人が自分自身のGoogleアカウントでAdSenseアカウントを作成し、収益をその保護者・後見人が受け取る形になります。

### 公開後に確認すべき項目

- プライバシーポリシー・利用規約・お問い合わせページが実際にアクセス可能か
- サイトが正常にHTTPSで表示されるか
- コンテンツ量が十分か(記事・お店情報が実データに差し替わっているか)

### 不承認になった場合の改善方法

- 不承認理由(メールで通知される)を確認し、該当箇所を修正
- コンテンツ量・独自性が不足している場合は、記事・お店の登録数・口コミ等を増やしてから再申請
- 再申請には一定期間を置く必要がある場合があるため、Googleの案内に従う

## 21. 広告配置

「ユーザーが本当に情報を見に来るページ」に、**固定数に縛られない広告スロット方式**で配置しています。トップページはセクションの区切りごとに広告枠を挟む構成です。

**トップページの広告配置(上から)**:

```
TODAY(今日の時間割)
↓ home-slot-1
明日の時間割 / 今日・近日の課題
↓ home-slot-2
次の行事・出席率 / お知らせ / 今月の授業
↓ home-slot-3
大空町のお店
↓ home-slot-4
O-schoolの記事
↓ home-slot-5(ページ最下部)
```

**その他のページ**: 月間時間割(上部・下部)/ 今月の教科回数 / 学校行事 / 課題一覧(共有タブのみ)/ 大空町のお店一覧・お店詳細 / O-schoolの記事一覧・詳細 / 検索結果(結果がある場合のみ)

**広告を表示しないページ**: ログイン・新規登録 / 個人設定 / 個人課題(タブ)/ 個人の出席記録 / 日別時間割詳細 / エラーページ・404ページ / 管理画面 / お問い合わせ・プライバシーポリシー・利用規約

広告枠は `AdSlot` テーブルで管理し、`<AdSlot placement="xxx" />` という**再利用可能なコンポーネント**として各ページに埋め込んでいます。新しい配置箇所を増やしたい場合は
コンポーネントを1行追加し、対応する `AdSlot` レコードを1件登録するだけで済む設計です(管理画面`/admin/ads`から**枠ごとに個別ON/OFF**、または**サイト全体で一括OFF**が可能)。
現時点では実際の広告事業者と未契約のため、広告枠には「広告(未接続)」というプレースホルダーが表示され、実際の広告タグは埋め込まれていません
(`src/components/AdSlot.tsx` を参照)。ギガファイル便のように広告枠を多く持つ設計は参考にしていますが、**広告の量や表示方法をそのまま模倣してはいません**
(自動更新・クリック誘導・不正PV水増し・広告とコンテンツの混同といった規約回避行為は一切実装していません)。広告であることは常に小さく「広告」ラベルを表示しています。

## 22. 収益シミュレーター

`/admin/revenue-simulator` に実装済み。ユーザー数・1ユーザーあたりPV・訪問頻度・広告表示率・RPMを入力すると、月間PV・広告表示回数・推定月収/年収・1ユーザーあたり収益をリアルタイムで試算します。

同じ「ユーザー数50人」でも、毎日使う50人と月1回しか来ない50人では月間PVが最大30倍近く変わることを体感できます。これは本サービスの設計思想
(トップページを「毎朝開くダッシュボード」にし、時間割→課題→行事→お店→記事へ自然に回遊できる導線を作ることで、毎日の再訪とページ回遊を両方増やす)に直結しています。

## 23. 収益KPI

`/admin/analytics` に実装済み。DAU・MAU・PV・セッション数・広告表示回数・CTR・CPC・RPM・推定収益等をリストアップしていますが、
**実際のアクセス解析・広告配信サービスと未接続のため、すべて「未接続」と表示**しています。ダミー値を実際の収益であるかのように表示することはしていません。

## 24. セキュリティ

| 対策 | 実装内容 |
|---|---|
| SQLインジェクション | Prismaによる自動パラメータ化 |
| XSS | Reactの自動エスケープ。記事本文・口コミ本文等はすべてテキストとして描画(`dangerouslySetInnerHTML`未使用) |
| CSRF | Next.js Server ActionsのOriginヘッダー検証 |
| 認証 | bcryptjsによるパスワードハッシュ化、httpOnly+SameSite=lax Cookie |
| 権限管理 | `role`(STUDENT/ADMIN)による認可。`proxy.ts`+各ページ/Server Actionでの二重チェック |
| 管理者ページ保護 | `/admin/*`は未ログイン→ログインへリダイレクト、非管理者→トップへリダイレクト |
| 投稿内容のサニタイズ | 個人攻撃・電話番号・住所・SNSリンク等を検出する簡易フィルタ |
| 画像アップロードの検証 | MIMEタイプ(jpeg/png/webpのみ)とサイズ(3MB上限)をサーバー側で検証 |
| Rate Limit | ログイン試行・新規登録・投稿・写真アップロード・通報・お問い合わせにインメモリのレート制限を実装 |
| 不正アクセス対策 | セキュリティヘッダーを`next.config.ts`で全ページに付与 |
| 一般ユーザーが管理者権限を取得できないこと | 新規登録は常に`role: STUDENT`固定 |

## 25. モデレーション

- お店の写真・口コミには通報機能があり、通報理由を選択式で送信できます
- 管理画面の「お店の通報」ページで、対象の写真・口コミを確認しながら「非公開にする / 対応済みにする / 却下する」を選べます
- 投稿者本人は自分の写真・口コミ・個人課題をいつでも削除できます
- 悪質なユーザーは「ユーザー」ページから利用停止にできます
- 記事は管理者のみが作成・編集できるため、記事自体には通報機能を設けていません(コンテンツの質は管理者の責任で担保する設計)
